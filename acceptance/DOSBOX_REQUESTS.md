## Decisions needed

### R-1 addendum (dosbox-ref, 2026-10-16): colour 3 turns white after the first ground combat
All SCREEN 1 references taken before any PLBATTLE visit show attribute 3 light grey; every SCREEN 1 screen captured after a ground combat (run 4: IN-02r, IN-02c, IN-02w, SP-13, and the SPACE console after it) shows attribute 3 **white (255,255,255)**, with colours 1/2 still the module's PALETTE remaps. So in the original the low-intensity palette holds only until the first SCREEN 7 module has run; from then on attribute 3 is drawn white (whether the unremapped attributes also switch to the high-intensity set cannot be seen: the modules remap 1 and 2 with PALETTE, 0 is black). The SC-2 engine (always grey) matches the original before the first ground combat only. Evidence: `compare.py` maps `ffffff->aaaaaa` for IN-02c and SP-13 against the SC-2 shots, `aaaaaa->aaaaaa` for every earlier ref.

### R-1 — SCREEN 1 colour 3: light grey (original EGA) or bright white (current engine)? (raised by build-engine, 2026-10-16)

**What the original shows.** Every DOSBox-X `machine=ega` reference of a SCREEN 1 screen draws attribute 3 (the text, frames and lines colour) as **light grey (170,170,170)** and contains no white at all: 49 references - SU-01..04, PT-00, PT-02..PT-15, SP-01..SP-11, SB-01..SB-04, IN-02..IN-14 (survey: per reference the count of grey pixels, e.g. SU-03 14395 grey / 0 white, PT-02 11152 / 0, SP-01 4995 / 0, IN-02 20625 / 0; script `acceptance/ref/engine_fit/grey.py`). The modules run `COLOR 0,1` (CGA palette 1) and on an EGA remap only attributes 1 and 2 (`PALETTE 1,9: PALETTE 2,4`, INSIDE `1,2: 2,6`), so attribute 3 keeps the EGA BIOS default for SCREEN 1 palette 1, which is EGA colour **7** (low intensity: 0 / 3 cyan / 5 magenta / 7 light grey). Two SCREEN 1 references show white instead (IN-02c, SP-13): worth a look by dosbox-ref (captured in another palette state?), they do not change the picture. PLBATTLE (SCREEN 7) uses true white (colour 15) in both the original and the engine.

**What the engine shows.** `game/engine/display.js` paletteReset()/colorScreen1() map SCREEN 1 palette 1 to the high-intensity set 11 / 13 / **15**, so at all of those grey pixels the engine draws **bright white (255,255,255)** (same survey: e.g. SU-03 14395 of 14395 grey pixels are white in the engine shot). Geometry and text are unaffected; only the colour differs.

**What SC-1 = B implies.** SC-1 = B: "same content, layout and behaviour per screen as the original run in DOSBox; palette/resolution enhanced to 640x200 EGA 16-colour". Colour differences are therefore allowed and are not defects (ACCEPTANCE lists them as expected). But the EGA look is exactly what SC-1 names as the target, and the original's EGA look has grey, not white: the white is not an enhancement the game ever had, it comes from my engine default (I guessed high intensity on day 1, before any reference existed).

**Options.**
- **A (recommended): match the original's EGA colours** - SCREEN 1 palette 1 = 0 / 3 / 5 / 7 (palette 0 = 0 / 2 / 4 / 6), one table in display.js; the module remaps stay as they are, so the screens read exactly as on a 1988 EGA. All SCREEN 1 engine shots change colour 3 (regenerated by colour substitution, the same validated method as the F-1 font regen) and the reviewers' colour notes shrink. Text on the blue/red panels is slightly less bright.
- **B: keep bright white** as a deliberate enhancement under SC-1 = B (crisper text on the handheld screen); ACCEPTANCE keeps listing "colour 3 white vs grey" as an expected difference on every SCREEN 1 row.

Decision needed. Engine work after A: about 10 minutes plus the shot regeneration.

Extra findings (no request open):
- **Font (qa fix request F-1, build-engine):** the 8x8 glyphs the EGA BIOS supplies in SCREEN 1 were captured with a 58-byte test program (`scripts/mkfontcom.py`, all 256 codes via INT 10h AH=09h): `acceptance/ref/font_dosbox_ega8x8.json`. 4 of 256 differ from `game/assets/font8x8.json` (VileR's CGA ROM font): 0x05, 0x06, 0x0F and **`S` (0x53): original 78 CC E0 70 1C CC 78 00, engine 78 CC 60 30 18 CC 78 00** - every `S` on every screen differs by 2 px. Only `S` occurs in the game's text.
- **Rule-book check (qa fix request F-5, STARPORT owner):** STARPORT 09C1B-09C26 is `sub dx,bx / and dx,dx / jge / neg dx` = **ABS(ASC(typed) - ASC(word))**, not the plain negation STARPORT.bas.md 09C2E renders; a letter passes when it equals the word's letter +-1 or differs only in case (Diff 32). In the original, typing `zzz`/`xxxx` failed (`Wrong!`, new question) and `aaa` passed with the shipped placeholder words; the engine (starport.js 6290, -(typed - word) <= 1) accepts any letters from the word's letter - 1 upward, e.g. `zzz`. `scripts/abs_audit.py` checked every other `and/jge/neg` idiom in all listings: all others negate a 0/-1 comparison (ABS = negation there), so this is the only wrong one.
- **CIRCLE (qa fix request F-2, build-engine):** the SPACE console's rounded panels and ship ring (CIRCLE + PAINT, SUB_1023) differ from the original by 1 px steps along every arc (SP-01 diff: ~600 px on the arcs).
