Method: SPACE.bas.md contains 2,516 offset-tagged lines; 25 are the data tail at >= 99B4 (marked `' asm` in the pseudocode) leaving **2,491 code statements**. **10% = 250 statements were drawn with `random.seed(20261015)`, `random.sample`** (seed listed as required), plus every CHAIN/BLOAD/ON GOTO/ON GOSUB/INPUT statement not already in the draw (30 more) = **280 statements re-derived from the listing bytes**. ## Disagreements

**D1 (systematic, all 6 DISAGREE rows and 29 further unsampled sites): every `PUT ..., OR` in SPACE.bas.md is actually `PUT ..., PSET`.** The listing sets the verb with an immediate `mov dx, 3` before all 35 such CALL RT3E_58 sites (014B1, 01D2F, 01D63, 01D7D, ..., 08F27); under the corrected enum (RT_LEDGER 3E_58 after commit c19a327: **0 OR, 1 AND, 2 PRESET, 3 PSET, 4 XOR**; proven from the raster-op tables DS:0x368/0x372 in the glm-review-rt pass) `3` = PSET (plain blit), not OR (masked union). Root cause: `decode/pseudo/tools/qb2bas.py:551` still maps `{0:'PSET',1:'PRESET',2:'AND',3:'OR',4:'XOR'}` — the pre-correction enum. The 50 `XOR` labels (dx=4) are correct. The sampled DISAGREE rows are 01D66 (ShipHead2), 020E3 (Digit5), 0263B (HdrLongRange), 034B5 (HdrVisual), 08E86 (DropShip3), 08F2A (SaveArea); the other 29 dx=3 sites are the same one-line defect. **Impact**: a repro built from this text would composite sprites over the background instead of replacing it — every sprite draw in SPACE is affected. `SPACE_SCREENS.md` repeats the same OR labels (e.g. `PUT (154,0), Logo, OR`) and needs the same fix after regenerating with the corrected map. Fix: change the qb2bas.py map to `{0:'OR',1:'AND',2:'PRESET',3:'PSET',4:'XOR'}` and regenerate; note for the Foreman: **other module outputs generated by qb2bas.py carry the same stale map** (fix before the remaining modules' final passes).

Minor notes (no verdict change):
- **RT_LEDGER 3F_B7 type-byte wording**: the ledger's "(04 single, 03 string, 02 integer, 08 double)" describes the post-xlat value-type codes, not the inline bytes. The B7 body xlats inline codes through DS:0x707: inline 01->02 (integer), 02->04 (single), 03->08 (double), 04->03 (string). SPACE uses inline 04 for ShipName$/CrewName$/MissionText1$2$ (strings — rendered correctly) and inline 02 for Scratch! (single — rendered correctly); only the ledger prose could mislead a future reader.
- 0x6C2C (used in `G!(FNIdx(6,9)) = 9` at 00941 and the FNKey tail at 0444E) is an init literal 9.0, not a variable — the pseudocode correctly renders the constant; noted because a naive read of the listing (`mov si,0x6c2c`) suggests a named variable.
- The pseudocode's 21DF manual-correction note (in SPACE_header.md) matches my independent decode of 21C0-21E1 (`mov bx,0; jae; dec bx` = Cmd!<12, `mov dx,0; jbe; dec dx` = Cmd!>37, `or dx,bx; je` -> reject non-letters); the generated body line is already flagged by the lane itself.
