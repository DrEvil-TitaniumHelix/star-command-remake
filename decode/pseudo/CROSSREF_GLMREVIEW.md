Method: every claim of sections 1-5 (and the §6 re-check) was re-derived from the cited offsets in the listings, with the operands resolved against the literal tables and the names files; the COMMON index collision check was done programmatically over all five names files (every address in 0x1850..0x7FAA named by more than one module, compared by name); the NAME file was re-parsed with the INPUT quoting rule.

**Verdicts: 71 claims checked - 60 AGREE, 5 DISAGREE, 6 UNSURE (not re-derived: the IN-n / INSH / INFO / MAP-n formats, the PALETTE sites, the SPBATTLE MoveDX/DY and INSIDE FirstRow! roll-up items, the CHAIN *conditions* of STARTUP 0AFF and STARPORT 9F3F).**

## Disagreements

**D1 - §2.2 row 2254, §5 #2, §6 bullet 2: the INSIDE 0D51 polarity is reversed.** INSIDE 00D43-00D53: `mov si,0x87FA (0.0); mov di,si; mov si,0x3B88; RT3F_9F (FCMP [SI]?[DI]); je 0xD56; jmp 0xD6B`, and 0D56-0D68 = `X! = OldX!; Y! = OldY!; GOTO L_0DAA`. So **when BattleWon! = 0 (lost or fled) the squad is put back on OldX!/OldY! (the cell it came from); when nonzero (won) it stays on X!/Y! and goes to L_0D6B (0D86 RoomNo! = INT(FNCell(0)/64), 0DA4 InMap%(FNRoomIdx(RoomNo!, 1)) = -1 = the room is marked)**. CROSSREF says the opposite ("restores OldX!/OldY! (the squad stays where it fought) only when nonzero"; "keeps the squad on its battle cell only when it won (else L_0D6B)"). INSIDE.bas.md's body line is right (`00D51 IF N_3B88! <> 0 THEN GOTO L_0D6B`), INSIDE_names.json's `_why` for 3B88 carries the reversed reading ("nonzero -> X!,Y! = OldX!,OldY!"), and CROSSREF inherited it. The engine is right: inside.js line 342 `if (ne(G[2254], 0) !== 0) { pc = 0x0D6B; ... }` then 0D5C/0D65 restore - so this is a documentation defect only (CROSSREF + INSIDE_names.json), no code change. Fix text: "INSIDE 0D51: BattleWon! = 0 -> X!,Y! = OldX!,OldY! (the squad is pushed back off the encounter cell); nonzero -> stays on the cell and the room is marked (0D86-0DA4)".

**D2 - §5 #4: `Difficulty!` (SPACE 0xAB8C) is assigned.** SPACE 00F3A-00F40 `Difficulty! = 0` (`mov di,0xAB8C; mov si,0x6C24 (0.0); RT3F_7B`), then 00F49-00F7F `FOR I! = 110 TO 159: IF G!(I!) > 0 THEN Difficulty! = I! - 110` (00F70 `mov di,0xAB8C; RT3F_7D` after `FADD [I!] + [0xAB94 = -110]`). So Difficulty! = the index of the highest mission flag G!(110..159) that is nonzero, minus 110 (0..49 = how far the mission list has progressed; 0 when none). It feeds `EnemyType! = INT(Difficulty! * 5 / 50)` (06BD1) and the found-item range (060A0). CROSSREF's "never assigned in SPACE ... so it is 0 (item range 0..3, enemy strength base 0)" is wrong; SPACE.bas.md lines 00F40/00F73 already show both stores and space.js lines 347/353 implement them, so again a CROSSREF-text defect with no code impact - but a repro built from §5 alone would always roll the weakest surface enemies.

**D3 - §2.5 (and the wording of §2.1): the sprite banks ARE inside the declared COMMON block of the modules that share them.** Module header words 20/21 (= `common_start`, `common_len` in `_*.json`): STARCOMM 0x1850 + 0x28A4 (ends 0x40F4: the G!() array only), STARTUP / STARPORT / the four .STR stubs 0x1850 + 0x3040 (ends 0x4890 = right after ShipName$ 0x488C: G!() + the 20 string arrays + ShipName$), **SPACE and SPBATTLE 0x1850 + 0x524C (ends 0x6A9C)**, **INSIDE and PLBATTLE 0x1850 + 0x67DA (ends 0x802A)**. Each module's own literals start exactly at that end (SPACE 0x6AA2 "###" / 0x6AAA Drive$, SPBATTLE 0x6AA2, INSIDE 0x827C 1.0 / 0x8274 Drive$, PLBATTLE 0x804E 1.0, STARPORT 0x4F6C 1.0 / 0x4F78 Drive$). So SPACESH.BAS at 0x4890 and SHIP-n.BAS at 0x65FC lie in the COMMON block that SPACE and SPBATTLE declare in common (0x4890..0x6A9C), which is why SPBATTLE can PUT from SPACE's banks after a CHAIN without loading them: BRUN keeps the declared COMMON extent. Likewise INSIDE's squad position X!/Y!/OldX!/OldY! (0x48A0..0x48AC) and the rest of 0x4890..0x802A are common to INSIDE and PLBATTLE (PLBATTLE_names.json already says "0x40F4..0x7FAA = other COMMON variables"). CROSSREF's practical advice (keep the banks loaded or load them in SPBATTLE) stands; the sentence "are **not** COMMON ... so SPBATTLE relies on SPACE's banks still being in memory" and §2.1's "all game modules and the four stubs declare the same COMMON block" should say: the first 0x3040 bytes are the shared vocabulary of §2.2, and the module pairs SPACE/SPBATTLE and INSIDE/PLBATTLE extend it (0x524C / 0x67DA), STARCOMM declares only G!().

**D4 - §1.2: the program-exit list is incomplete.** Besides STARPORT 9D99 (`Quit the game? (Y/N)` = Y -> END) the game also ends with `END` at **SPBATTLE 3098** (life-support failure: "support systems your air runs out." 03057, "You Are All Dead" 03072, a 15-second TIMER wait 03084-03096, then `RT3E_01`), and STARPORT 9F42 holds an unreachable END after the CHAIN. PLBATTLE's "You Are All Dead" (436B) is an endless `jmp 0x436b`, as CROSSREF implies. The reachability graph itself is right.

**D5 - §2.4 "used by" and §2.6 rename lists are incomplete for PLBATTLE / INSIDE.** PLBATTLE reads `WeaponName$` (0x43F4: INPUT at 055D in the debug path, printed in the attack line) and `HandWeaponName$` (0x44CC: 059F, printed at 06C76 `PRINT HandWeaponName$(CINT(HandWep!))` in the live path), but §2.4 lists 43F4 as "STARPORT, SPACE, INSIDE" and 44CC as "STARPORT" only. §2.6's INSIDE list lacks `3B88 N_3B88! -> BattleWon!` (the only COMMON address, apart from the by-design `G!`/`EngineCond!` alias at 0x1850, that two modules still name differently - see the collision scan below).

Minor notes (no verdict change): (a) CROSSREF cites the STARCOMM / STARTUP CHAIN sites as 0119 / 0AFF; the `RT3E_0E` calls are at 0011C / 00B02 (0119 / 0AFF are the `mov bx,<name>` statement starts of the hand-written pseudocode) - same statements. (b) §1.1 SPACE 6E0B lists `Gravity10!` among the values set before the CHAIN; it is not written in the 6DC6-6E0B block but at 5BF1 (`Gravity10! = table * 10` when the planet is scanned) - the value is carried, the wording is loose. (c) SPACE 6DD8 copies the variable SPACE names `PortNo!` (0xB006) into `Surprise!` - the SPACE owner may want to note that 0xB006 is reused as the surprise code there (0/1/2 per PLBATTLE 01D3-01F5). (d) §5 #1 says "PLBATTLE pending for 83/87": settled - no listing except STARTUP references 0x199C / 0x19A0 / 0x19AC / 0x19C0 (the PLBATTLE grep hit at 01993 is a `jmp 0x19c0` code target, not a data reference). (e) §2.3 has no rows for crew fields 51..53 (PLBATTLE's esper-derived fields, 1F7D-21E3, e.g. 0342C/03473 in the debug fill) and 58 (PLBATTLE stamina = 3 x field 8, 22A8); they are PLBATTLE-internal, so a one-line addition is enough.
