## 2. Escape hatch (18e1c14 + seam 1954d78): FAIL

Working as specified: the device()/modal routing (input.js:74-77); code-pushed keys bypass the overlay (push()); Esc/Start/Back/B (outside Y/N) open it; Resume forces a re-present; pause gates timer frame/wait/delayLoop (wrapped on the shared E.timer object, which STARPORT, STARTUP and the space-family runtimes all call at call time) and freezes TIMER and the audio clock; click hit boxes match the drawn rows. CHARINFO/CHARNAME bytes match 09CF3-09D6D: `E.state.save()` is exactly STARPORT's rt.bsave, and the names are written as `name,` x9 plus Ctrl-Z, as starport.js close(). The departure checkpoint is consistent with CROSSREF section 1 / STARTUP 0AFF: ChainArg! still holds the port (STARPORT never writes it), and 09ED5-09F33 only set EntryMode!/date/crew field 54. The IN/INMAP journal is cleared only at STARPORT departure, so starport-time and returned-voyage map writes are never rolled back. No module reads ESC: SUB_22C4 never returns -37.

Defects:

- **E-1 (a save that a later load continues incorrectly), overlay.js:92-93, 99-102.** `live = E.currentModule === 'STARPORT'` saves the current COMMON at any point inside STARPORT, not only at the native save point (main menu). Scenario: you arrive at a starport with kills since the last starport. Arrival processing pays each kill reward (STARPORT 01763-01766 SUB_1E98 adds the credits, then 01775 waits on "Press ENTER Key"). KillStartPort! is reset only after the whole loop (01844), and tow entries are cleared only after each one is paid (0188E). Press Esc on the first reward screen, then S. The save holds the reward credits and the uncleared kill/tow markers. The next load enters STARPORT, re-runs arrival and pays the rewards again (duplicate credits). The same class applies to any multi-step STARPORT transaction. Fix direction: treat STARPORT as live only while it waits at the main menu (L_210D/PT-02). Otherwise save a checkpoint taken at the last main-menu wait (or at arrival entry) and say so on the overlay.
- **E-2 (a game hotkey leaks into the overlay), input.js:168-174 (with 160-166).** padButton('A') with a highlight sends the highlighted game-menu letter through device(), and while the overlay is open that letter goes to modal.key(). LB/RB still move the game highlight while the overlay is open, and pad B returns before clearing it. Scenario in IN-02: RB to highlight `S-Search`, then pad B (not a Y/N prompt) opens the overlay with Resume selected. Pad A (meant as "Resume") sends `S`, which is Save & Quit, and the window closes. With `R-Reload` highlighted it is Resume. In any screen with an `S-` or `Q-` item it is Save & Quit or Quit without saving. Fix: ignore the highlight path (and LB/RB) while `this.modal`, and clear the highlight on open.

## 3. Mouse (b0f2bf3): FAIL

Working as specified: every click goes to `input.device(r.key)` (pointer.js:134-139); modal clicks are isolated; only the cursor style changes and nothing is drawn, so screens without mouse input are unchanged (IN-02/SB-02 reshoot unchanged; the PUT wrapper only samples pixels). The map geometry matches the decode: INSIDE marker (X!*5+8, Y!*5+7) at 0x48A0/0x48A4; SPACE long range CellX = SectorX mod 8 (0269x); sector CursorCol!*7.46+16; system SysCurX!*8+20; PLBATTLE SquadIcon (GrpX!(5)*8-8, GrpY!(5)*8-8) with steps of 1. The IN-10 rows match 069C8 (`>` at row 20). The harness matrix itself is self-consistent (click == key), but it cannot catch regions on non-hotkey text, or hotkeys with no region.

Defects:

- **M-1 (wrong key sent), pointer.js:9-12 + 24 + 74-90.** A selector's span runs to the next double space or the next `X-` selector, and disjointRegions gives the earlier region precedence. On the STARPORT ship browser (PT-04 C-Buy Ship, 05269 `B-Buy the Ship, ENTER to Exit`) the `B` region therefore covers the whole row and the `ENTER` word region is removed completely. Clicking the printed "ENTER" (Exit) sends `B` (Buy the Ship). Verified with textRegions/disjointRegions on that line: one region `B` at x 8..240, no CR region.
- **M-2 (region on non-hotkey text with a different meaning), pointer.js:9 (`X>` pattern).** The SPACE/SPBATTLE crew-panel slot tags (`SlotTag$ ">"`, SP-00 rows 11-18, which SCREENS_INDEX lists with keys "-") become selectors. On SP-01, clicking the co-pilot row `C>Lane` sends `C` and opens the Computer menu (SP-06). The harness shot starcommand-mouse-space-final/SP-01-01-click.png shows exactly that. On SB-02 the same click runs C-Scan (SB-03). These tags are hotkeys only inside SP-05/F-Switch pickers. `P>`/`1>`..`6>` are dead pointer targets on SP-01/SB-02/PB-04/PT-02.
- **M-3 (hotkeys without a region), pointer.js:9 (and input.js menuItems).** Both detectors require whitespace before the letter, so the STARPORT weapon-class chart (PT-04 A-Buy Personal Equipment, 03A70/03AA2/03ACE/03B86: `-G-Bullet`, `-B-Bullet`, `-J-Laser`, `-F-Gernade`; CmdMax! = 12 at 03BCC) has no click targets for G, B, J or F. The owner section 1 says every element that reacts to a key must react to a click. The other 8 of 12 work.
