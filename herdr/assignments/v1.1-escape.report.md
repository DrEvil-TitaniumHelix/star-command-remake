## Design

`installEscape(E)` installs the existing device escape callback and modal key/click handlers. The menu draws through `display.overlays` in 640x400 coordinates, using the engine's IBM 8x8 glyphs at 2x scale and EGA colors. It never writes menu pixels to the framebuffer. Resume forces a fresh presentation. R/Esc/pad B resume, S saves and quits, Q quits; arrows wrap the highlight and Enter/pad A confirms. Pointer hit boxes use logical coordinates, matching the drawn rows. No module has an original Esc use to preserve. Programmatically pushed keys still bypass the modal by the input seam's design.

Timer frame/wait completions wait behind a resume gate, including waits already in progress. Timed waits preserve their remaining duration across a pause; TIMER freezes while open and excludes paused time afterward. Audio's queue clock freezes and an existing running AudioContext is suspended/resumed. Audio unlock is suppressed while modal so navigation keypresses cannot resume it early. Pausing is cooperative at the existing asynchronous timer/input/audio boundaries; JavaScript work already running cannot be preempted. Fetch completions and arbitrary external promises are not globally suspended. This needs no edits to timer.js or audio.js.

Both quit paths call `window.close()`. After 300 ms, if execution continues, the framebuffer is cleared and the overlay displays `You can close this window.` The modal remains installed so the game cannot receive device input after quit. The local server is left running. Save errors retain the modal, show an error note, and permit R to resume.

## Save contract and per-module policy

CROSSREF section 1 and STARTUP 0AFF establish that loading always enters STARPORT. A raw SPACE/INSIDE/battle entry snapshot is therefore not a valid resume point: ChainArg may identify an encounter instead of a port, battle state is local, and crew names may be shifted. We deliberately retain the last **starport departure** checkpoint for all these modules. The note is visible before S is pressed: `Saved as of starport departure`. When a direct developer jump or initial STARTUP session has no checkpoint, the fallback is the existing disk save, with `Saved as of last disk save`.

| Current module | Save behavior | Why / local files |
| --- | --- | --- |
| STARPORT | Current COMMON, current ship and eight crew names; note `Save current starport state`. | This is the game's native saving module. SaveLock G[2265] is zeroed for serialization as at 09CDB, then restored in live memory. Uses `E.state.save()` and `E.data.writeText()`. |
| SPACE | Last starport departure; otherwise existing CHARINFO/CHARNAME. | Loading enters STARPORT, not the current sector. Current COMMON may have encounter/station ChainArg values unsuitable for a port. Travel since departure is rolled back. |
| INSIDE | Same starport checkpoint/disk fallback. | Squad name shifts and module-local enclosure/map data prevent direct saving. Native IN-n/INMAP-n writes occur in the exit routine at 063BB/063F5. Unwritten local maps are discarded with the visit. |
| SPBATTLE | Same starport checkpoint/disk fallback. | Current COMMON includes partial damage and an enemy ChainArg; local battle progression cannot be reloaded through STARPORT. |
| PLBATTLE | Same starport checkpoint/disk fallback. | Local tactical state, shifted crew names, enclosure/boarding return paths, and enemy ChainArg are not a standalone disk save. |
| STARTUP / STARCOMM | Existing disk save, unchanged numeric bytes. | STARTUP setup/calibration and new-game editing are not a native save point. The startup adapter runs both launch flows while currentModule may still say STARCOMM; both get the same fallback. |

The STARPORT departure checkpoint is captured by wrapping `E.chain` inside overlay.js, before the CHAIN signal unwinds the module. It owns copied byte-faithful MBF body bytes, header, and name strings. There is **no required chain.js patch**: every module's existing E.chain seam is sufficient, including startup's adapter. This avoids any dependency on an unmerged entry-snapshot patch.

CHARNAME matches STARPORT 09D12/09D31's PRINT-with-semicolon format: ship name plus comma, then each of eight crew names plus comma, no inserted quotes or CRLF, then Data.writeText's Ctrl-Z. Missing COMMON names use the disk fields as a fallback. Unchanged MBF fields preserve loaded bytes through State.toBytes; snapshots do not round-trip numbers through JSON or IEEE-only serialization.

A write journal retains each IN-n/INMAP-n file's previous persisted bytes on its first write after a checkpoint. A rollback restores those bytes, or removes the override when the previous version was the shipped file. This also undoes visits already exited during a rolled-back voyage, keeping the numeric checkpoint and map files together. A successful return to STARPORT uses the current state and keeps the native map writes; departure resets the journal for the next voyage. Other game file writes are not intercepted.

## README text for build-engine2 to merge

> Press Esc, or gamepad Start/Back (B outside a Y/N prompt), to pause and open Resume / Save & Quit / Quit without saving. Use R, S, Q; arrows and Enter; gamepad d-pad and A; or click an item. Esc/B also resumes. Saves use the original CHARINFO.BAS and CHARNAME formats. At a starport, Save & Quit saves current progress. Away from a starport it saves as of the last starport departure; the overlay states the checkpoint before you choose. If no departure checkpoint exists, the last disk save is retained. ## Open questions / limits for review

- The conservative policy intentionally rolls back an entire voyage, even quiet SPACE travel. More frequent saves require a specified STARPORT-compatible conversion of SPACE COMMON/ChainArg or a new resume format/routing mechanism; neither is needed for this implementation.
- STARPORT permits saving the current COMMON while an interaction is awaiting input, as requested for this module. If reviewers want rollback during partially completed purchases/crew editing too, that needs a finer native-menu checkpoint contract; no game-module edits were made here.
- Persistence inherits Files.write's current behavior: browser localStorage errors are logged by Files while memory writes succeed. Multi-file persistence is not transactional. This lane does not change that shared storage contract.
- Real hardware gamepad, audible output, and Chrome --app window.close need a manual smoke test; modal keyboard equivalents and synthetic pointer coordinates are covered here.

E-1: capture COMMON and names when currentModule enters STARPORT, before the module executes arrival processing (also capture on an incoming CHAIN). Retain a separate checkpoint at each main-menu wait. The rule is STARPORT + visible `Main Menu` and `Select Option` + an empty INKEY$ poll. Evidence: STARPORT.bas.md L_210D clears the menu area, 0211C prints Main Menu, 0214F prints G-Game Save, 0226C calls SUB_1E7C (01E88 prints Select Option), and SUB_22C4 polls INKEY$ at 022CA. The 0227D dispatch routes G to L_9AA7, the native save. No module edits are required. A consumed key ends the wait; visible menu text alone is insufficient.

At that wait Save & Quit saves current COMMON and says `Save current starport state`. Elsewhere in STARPORT it saves the most recent menu checkpoint (`Saved as of the starport main menu`), or this visit's entry checkpoint (`Saved as of arrival at the starport`). Entry/menu rollback retains the voyage's interior-map writes because it remains within the same STARPORT visit. Other modules retain their departure/disk policy. Long notes scale horizontally within the overlay box.

TIMER now subtracts a whole number of paused BIOS ticks and returns a quantised BASIC single. A missing name writes an empty field for that slot; it never replaces the other current names with disk names. SaveLock is zero in serialized bytes and restored in live memory, including protected mode.
