## Behaviour
- Toggle: `E.input.onDeviceHelp` (already called for device F1 and gamepad Back), plus a small corner button: a DOM element positioned over the canvas corner (bottom-right of `#screen`, outside the game picture is not available: put it as a semi-transparent 24x24 `?` button that only shows while the mouse is over the canvas). Off by default; never drawn when `E.settings.on('controlOverlay')` is false (settings.js: Classic mode turns it off).
- Content for the CURRENT screen, rebuilt every frame it is open (so it never goes stale): one line per distinct hotkey from `E.pointer.regions()` with its label text read from `E.text.screenText()` at the region (menus: the label; Y/N; ENTER/SPACE words; selectors `1>Ortiz` -> "1: Ortiz"; arrows: "Arrow keys: move"; map: "Click a cell: step toward it"), then fixed lines: gamepad mapping (d-pad = arrows, A = ENTER / highlighted item, B = N on Y/N prompts else Esc, X = SPACE, Y = Y, LB/RB = highlight menu items, Start = Esc menu, Back = this help), mouse (click a hotkey = press it; map zoom per v1.2 zoom when on), `Esc: Resume / Save & Quit / Quit menu`, `F1: this help`.
- Drawn with game/engine/ui.js `drawPanel` (shared style with the Esc overlay and the tooltips) through `E.display.overlays`, never into the framebuffer; place it where it covers least (e.g. right half), scale 1 if it does not fit at 2. The game keeps running and keeps its input while help is open (not modal); F1/Back closes it.
- Expose `E.help = { open, close, toggle, isOpen, lines() }` (lines() = the text model, used by the node test and later by v1.3's manual-on-demand).
