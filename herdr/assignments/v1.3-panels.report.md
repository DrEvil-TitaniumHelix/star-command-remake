## Design

The DOM crew panel uses spare viewport width only, shifts the centered canvas to make room, and never changes its integer scale. It is hidden below 300 spare pixels, outside SPACE/INSIDE/PLBATTLE, or when `crewPanel` is off. All eight crew records appear in a scrollable panel. SPACE adds fuel, armor, and all 23 equipment conditions. Squad names follow the modules' shift by two; pilot/communicator use role labels while their original names are absent from the shifted COMMON names. HP/max HP, current weapon, loaded ammunition and owned reload counts are read from COMMON; battle stamina is shown for the six squad members during PLBATTLE. Stamina outside that context is explicitly unavailable (—), since the decoded field is battle round state, not a continuously maintained INSIDE statistic.

The log book is an in-memory journal opened through a hover-revealed corner button, with Close and scrollable verbatim text. It watches screen text, CHAIN boundaries, and COMMON deltas. Printed briefing pages are retained verbatim with whitespace, along with mission/report/medal screens; STARPORT pages with the decoded ENTER prompt are retained as well so a second briefing page without a heading is preserved. Key dismissal observes before the picture can be replaced. Credits, deaths, special bonus flags, actual crew Medal of Honor flags, module arrivals/sector coordinates, cumulative kill/tonnage/win numbers, and PLBATTLE credits gained are recorded. No game key is consumed. All decoded indices/formulas have source comments.

No LOGBOOK write occurs during observation: it must be persisted with the same chosen checkpoint as CHARINFO. Existing saved LOGBOOK bytes are restored at installation. Installation in index.html follows the `?save=` application so prepared saves are read first.

## Required shared-seam merge: overlay.js / slots.js

The assignment reserves overlay.js for v13-settings and requests coordination through this report. These are required integration patches; the journal serialization API is implemented and tested, but Save & Quit is not connected until the owner merges them.

1. In `captureSave(E)` include a `logbook` property in the returned point:

```js
logbook: E.logbook?.checkpoint(),
```

Call `E.logbook?.observe()` before taking the checkpoint (before toBytes), so a departure/arrival/menu snapshot includes current journal events. The existing entryPoint/menuPoint/checkpoint selection then automatically carries the correct journal history, including rollback on non-starport saves.

2. In `quit(save)`, after writing CHARINFO/CHARNAME and rolling back IN files, add:

```js
if (point.logbook !== undefined) E.logbook?.persist(point.logbook);
```

For the fallback disk-save point leave `logbook` undefined: keep the existing LOGBOOK disk bytes exactly, just as the existing CHARINFO fallback is kept. Do not persist the live journal in that case. Quit without saving must never call persist. `persist` checks `logBook` at call time, so Classic / switch-off leaves the existing disk journal untouched. Include LOGBOOK writes in the overlay failure handling already surrounding save.

3. Named slots: include the raw `LOGBOOK` file (no `.BAS` extension) with slot file snapshots/restores. When loading a slot in the same engine instance, decode the restored file and call `E.logbook.restore(entries)`; if absent call `restore([])`. A page restart reads the restored file automatically. Slot autosave must pair LOGBOOK with the same arrival checkpoint as CHARINFO; call `persist(point.logbook)` before collecting slot files, when the property exists. The slot should not invent an empty LOGBOOK for a legacy save.
